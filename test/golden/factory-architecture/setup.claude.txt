# Task

Make the sync resumable across restarts, per endpoint, without re-downloading pages

Mode: design. Return it as `mode`.

## Step 0 — can the other vendors' CLIs run?
Some seats run through the Codex CLI and the Antigravity CLI (agy). Check that they can start from here before anything is created. Make one Bash call with the sandbox disabled (dangerouslyDisableSandbox: true), exactly as written:
dark-factory preflight --vendors codex,gemini
It prints JSON with a "status" and, under "vendors", an entry per vendor with "ok" and "error". Copy each entry into `preflight` (vendor, ok, error). If status is "ok", go on to step 1. Otherwise stop here: return status "preflight" with the entries, and empty values elsewhere. Don't try to fix it, and don't run anything else.

## Step 1 — the documents the work follows
The seats work in git worktrees checked out from HEAD, so they can't see uncommitted files. If the task follows a plan, a checklist, a spec or notes that aren't committed, the seats would never see them.
Read the task for any other document it tells the seats to follow or read, for example "item 13 on BUG_CHECK_LIST.md" or "implement docs/plan.md". Resolve each named file against the repository root (and ~/.claude/plans/ for a plan named there), and check that it exists. Only documents, not source files the task merely mentions.

## Step 3 — the verification command
If the task or a document from step 1 names commands the change must pass (a "Done when" section, acceptance criteria, a checklist), the verification command runs all of them, joined with &&, even when they include static analysis or coverage: every role is measured against this command, and one that leaves a required check out makes each of them run it separately. Otherwise, find the project's standard command for checking a change: its test suite, from CLAUDE.md or AGENTS.md, a Makefile, composer.json, package.json, pyproject.toml and so on. Prefer the normal test run. Avoid full static-analysis sweeps and very slow suites unless the task is about them. If the project has no tests, there is no command.
Write it to <runDir>/verify.sh as just the command, with no shebang line; it is run as `bash verify.sh` from the root of a worktree. Write an empty file if there is no command.
Set baselinePasses to false and baselineNote to "".

## Step 4 — acceptance criteria
Write 3 to 7 acceptance criteria: concrete, checkable statements of what a complete and correct result must satisfy, derived from the task, the reference documents from step 1 (what they require for this task) and the codebase, not from any particular solution. They are the yardstick every position is judged against and they are fixed before anyone starts, so make them fair to different valid approaches. Read the relevant code before writing them. Number them C1, C2, ….
The seats deliver a design and a milestone plan, not the change, so write criteria the design must meet: what it must cover and decide, and what the finished work must do once every milestone is built.
Every criterion must be checkable by the route seats and verifiers actually have: reading files, and running commands from a worktree inside a sandbox, with no subagents, no `claude -p`, no network and no logins. For a design or an investigation, checking the document against the code is a fine route; not every criterion needs a command. Name the evidence in the criterion itself where it isn't obvious (a test, a command, a file to read). Don't write a criterion only a capability the seats lack could check.

Write <runDir>/TASK.md with the task (verbatim), the mode and what it means the seats deliver (for implement: the integrated change in their worktree, including the tests and docs the criteria ask for; in this run, a design ending in milestones, with nothing in the repository changed), the paths of the reference-document snapshots, the context if any, the acceptance criteria, and the verification command.
